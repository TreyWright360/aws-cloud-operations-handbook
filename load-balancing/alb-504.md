# ALB HTTP 504 investigation

**Evidence status:** DOCUMENTATION ONLY
**Related project:** [Multi-AZ web infrastructure](https://github.com/TreyWright360/aws-multi-az-web-infrastructure)
**Video:** Not recorded

## Failure symptom and customer impact

A client receives HTTP 504 through the Application Load Balancer (ALB). Record the request path, UTC time, frequency, and whether direct health checks still pass. A healthy `/health` endpoint does not prove that every application path or dependency is healthy.

## Current architecture

The project defines an [internet-facing ALB and target group](https://github.com/TreyWright360/aws-multi-az-web-infrastructure/blob/main/modules/alb/main.tf) forwarding HTTP port 80 to an [EC2 Auto Scaling group](https://github.com/TreyWright360/aws-multi-az-web-infrastructure/blob/main/modules/asg/main.tf). The target health path is `/health`. The current EC2 user data serves a static Apache page and health file. [RDS is provisioned](https://github.com/TreyWright360/aws-multi-az-web-infrastructure/blob/main/modules/rds/main.tf), but the page does not query it. A database latency demonstration therefore requires a separate application change.

## Evidence to collect

| Signal | Why it matters |
| --- | --- |
| `HTTPCode_ELB_504_Count` in `AWS/ApplicationELB` | Confirms ALB-generated 504s in the incident window |
| `TargetResponseTime` | Helps distinguish slow target responses from immediate failures |
| Target health state and reason | Shows whether target registration or health checks are failing |
| ALB access log, if enabled | Shows request path and processing times; **not enabled by current Terraform** |
| EC2 system/instance status and service logs | Separates host failure from application startup or request handling |
| Security group, NACL, and route path | Checks connectivity between ALB and targets |
| Dependency response time | Relevant only when the failing request actually calls a dependency |

## Diagnostic decision tree

1. **Confirm the source.** Is the response an ALB-generated 504? Compare the client response time with `HTTPCode_ELB_504_Count` and, when available, the access log. If the target itself returned 504, investigate the target application.
2. **Check target health.** If all targets are unhealthy, inspect the health path, registration, security groups, and ASG activity. Also investigate 503s; they indicate a different failure path.
3. **Check connection and response timing.** If target health is good but target response time rises for the failing path, inspect service logs, CPU/memory, and any dependency that path calls. If the ALB cannot connect to the target, inspect port 80 reachability, security groups, NACL return traffic, and instance status.
4. **Correlate with change.** Compare the incident start with a launch template, deployment, scaling, or network change. Avoid raising the ALB idle timeout until timing evidence shows it is the correct correction.
5. **Escalate when evidence conflicts.** Preserve the time window, request ID if available, metric view, target state, and tests already performed.

## AWS Console checks

In EC2 → Load Balancers, inspect the listener, target group, attributes, and access-log setting. In Target Groups, inspect health state and reason. In CloudWatch, compare 504 count and response time over the same UTC window. In Auto Scaling, inspect activity and instance replacement events. In EC2, inspect status checks and the instance security group. For NACLs, inspect both inbound and return traffic rules.

## Read-only CLI checks

Replace bracketed values with the lab resources. Set the region explicitly; these calls do not change AWS resources.

```bash
aws sts get-caller-identity --query Arn --output text
aws elbv2 describe-target-health --region <region> --target-group-arn <target-group-arn>
aws elbv2 describe-load-balancer-attributes --region <region> --load-balancer-arn <alb-arn>
aws autoscaling describe-scaling-activities --region <region> --auto-scaling-group-name <asg-name> --max-items 20
aws ec2 describe-instance-status --region <region> --instance-ids <instance-id> --include-all-instances
```

The [triage script](../scripts/aws/triage_diagnostics.sh) can collect the ALB, target, and optional ASG views in one read-only run.

## Containment, remediation, rollback

If one target is demonstrably bad and healthy capacity remains, use the project's approved replacement or deployment procedure. If a new version caused the issue, restore the last known good launch template or application version after checking capacity. For a confirmed network rule error, make the narrow rule correction and record the prior rule so it can be reverted. For a slow dependency, mitigate that dependency or route safely around it; changing timeout settings alone can hide the problem.

## Recovery validation

Repeat the original request path from a client, not only `/health`. Confirm a successful response, healthy targets across intended AZs, falling 504 count, and normal response time over an observation window. Record the duration from fault injection to successful request. If the path uses a database, verify read/write behavior separately.

## Lab simulation plan

1. Deploy the reviewed lab stack and capture Terraform revision, region, ALB ARN, target group ARN, and baseline requests. Estimate cost before deploying and destroy the lab afterward.
2. Add ALB access logging and a 504 alarm in a reviewed infrastructure change; neither exists in current Terraform. Verify their operation before the episode.
3. Add a controlled application path that intentionally delays beyond the ALB idle timeout, or inject a reversible target connectivity fault. Record the exact fault and rollback method. The current static page cannot demonstrate a database-induced timeout.
4. Send bounded test requests, capture the 504 response, target health, CloudWatch metric, and access-log excerpt. Avoid a sustained load test.
5. Remove the injected fault. Capture a successful request for the same path and the post-recovery metric window.
6. Redact and commit a dated `evidence/alb-504/INDEX.md` with before/after artifacts. Upgrade the status label only after that proof exists.

## Interview explanation

“I first determine whether the ALB generated the 504 or merely forwarded a target response. Then I correlate target health and response timing with host, network, and dependency signals. I make the smallest reversible correction and verify the original client path, not just the health endpoint.”

## Limitations and production improvements

The current project has no ALB access-log configuration, no 504 alarm, and no application-to-RDS request path. Its workflow exits on failed post-deploy health checks but does not roll back Terraform or application versions. Those capabilities should be implemented and tested before a video claims to demonstrate them.
